# Orders

Manual orders from the Terminal's ticket and the API. The autopilot places its orders through the same `place_order`: stock buys as `day` limit orders capped 2% above the decision price, everything else as market orders (see [systematic.md](systematic.md)). A buy whose price cannot be read is refused, since it cannot be checked against the cash. Why these rules, and what Alpaca does with each: [trading-research.md](trading-research.md).

| Endpoint | What it does |
| --- | --- |
| `POST /orders` | place an order |
| `GET /orders?limit=` | newest first, with the prices, class and time in force |
| `PATCH /orders/{id}` | change an open order's quantity, price or time in force; it comes back as a new order |
| `DELETE /orders/{id}` | cancel, and say where the order stands |
| `DELETE /orders` | stop every working iceberg and algorithm order, then cancel every open order |
| `GET /orders/rules?symbol=&qty=` | the order types and time in force available for this symbol and quantity |
| `POST /orders/iceberg`, `GET /orders/iceberg`, `DELETE /orders/iceberg/{id}` | place, list and cancel an iceberg order |
| `POST /orders/algo/preview` | the slices an algorithm order would run on; nothing is placed |
| `POST /orders/algo`, `GET /orders/algo`, `DELETE /orders/algo/{id}` | place, list and cancel an algorithm order |

**Types.** `market`, `limit` (`limit_price`), `stop` (`stop_price`), `stop_limit` (both) and `trailing_stop` (`trail_price` in dollars or `trail_percent` from 0.1 to 25, one of them). A stop becomes a market order when the last trade reaches it, a stop-limit a limit order. A trailing stop follows the best price by the trail and, like a stop, works in regular hours only.

**Exits.** `order_class` `bracket` is a buy with both `take_profit` (a limit) and `stop_loss` (a stop, or a stop-limit when `stop_loss_limit` is given); the legs wait until the entry fills in full and one filling cancels the other. `oto` is a buy with one of the two. `oco` is a sell of a position already held, type `limit`, with both exits and no entry price. Bracket and OTO enter with a market or limit order.

**Time in force.** `day`, `gtc`, `ioc`, `fok`, by what the symbol and quantity allow:

| | market | limit | stop | stop-limit | trailing stop | bracket, OTO, OCO |
| --- | --- | --- | --- | --- | --- | --- |
| Whole shares | day, gtc, ioc, fok | day, gtc, ioc, fok | day, gtc | day, gtc | day, gtc | day, gtc |
| Fractional shares | day | day | day | day | none | none |
| Crypto | gtc, ioc | gtc, ioc | none | gtc, ioc | none | none |

**Checked before sending.** `OrderRequest` holds the table in `rules.py`, so a combination Alpaca refuses comes back as a 422 that names what is allowed ("Stop orders for whole shares accept day, gtc") and nothing is sent. Alpaca keeps the rules that depend on the market and the price: `ioc` outside market hours, price increments, a buy stop below the price, a trailing stop beyond 25% of the price, crypto orders under \$10. Its message reaches the ticket unchanged.

**Changing an order.** `PATCH /orders/{id}` takes any of `qty`, `limit_price`, `stop_price`, `trail` (the new dollars or percent of a trailing stop) and `time_in_force`; what is not sent stays. Alpaca replaces the order, so the answer is a new order (`replaces` names the old one, which becomes `replaced` and carries `replaced_by`), and a bracket's parent and each of its legs can be changed by their own ids. A change is checked against the order as it stands before it is sent: the order must be `new`, `partially_filled` or `held` (not `accepted`, `pending_new`, `pending_cancel` or `pending_replace`, and not finished); only the prices the type has can change; the quantity of a fractional order cannot change, a stock's must stay a whole number and above what has filled; the time in force must be one the type takes. Alpaca's own refusals (`order already replaced`, `order not found`) come back unchanged. A success does not guarantee the replacement: if the original fills first, Alpaca rejects the replacement and `order_replace_rejected` arrives on the stream. While a replace is pending, buying power is held for the larger of the two orders.

**Canceling.** `DELETE /orders/{id}` reads the order first and answers `{id, status, canceled, detail}`: an order that is already filled, canceled, expired, replaced or rejected is reported as it is and nothing is sent, and a cancel Alpaca refuses reports the status found afterwards. An unknown id is an error. `DELETE /orders` stops the working iceberg and algorithm orders first, so none can place another slice, then asks Alpaca to cancel every open order and returns how many were canceled, the ones that failed and how many icebergs and algorithm orders it stopped.

**Iceberg.** Alpaca has no hidden or reserve order, so this is client-side slicing: `qty` of a limit order at `limit_price`, `display_qty` at a time. One slice is a normal limit order on the book; when it fills, the next is placed, the last one with the remainder. A job checks every 3 seconds and calls Alpaca only while an iceberg is working. Each slice has a fixed `client_order_id` (`iceberg-<id>-<n>`), so a restart in the middle of placing one adopts the order that is already there instead of sending a second. Canceling the iceberg cancels the slice on show and keeps what filled. A slice replaced from the order table is followed to its new order, and its limit price carries on to the next slices; a slice canceled or expired elsewhere ends the iceberg (`canceled`, `expired`); a slice Alpaca refuses, such as for buying power, ends it as `failed` with Alpaca's reason; a busy broker or lost connection is retried on the next tick. Time in force is `day` or `gtc` (crypto `gtc`), and every slice must be an order Alpaca takes, so a fractional last slice needs `day`. While the API is down the remainder is not working; the slice on show still is. State is in `data/icebergs.json`.

**Algorithm orders.** `POST /orders/algo` runs a parent order as slices over a time: `algo` (`twap`, `vwap` or `shortfall`), `symbol`, `side`, `qty`, `duration` in minutes, `slices` (2 to 100, for a TWAP or a shortfall), an optional `limit_price`, an optional `tilt` (a TWAP's) and a `risk_aversion` (a shortfall's). Alpaca's own TWAP and VWAP need the Elite Smart Router and a paper account accepts them without running them, so the schedule runs here ([execution-research.md](execution-research.md)). A TWAP is `slices` equal intervals from now, a VWAP intervals cut at the five-minute marks. At each one the slice is its weight's share of what is left over the weights still to come, so a slice that fills short, a late start or a missed interval is spread over the rest, and the last interval sends everything left. Every slice is an `ioc` order, a market order or a limit at `limit_price` (a cap on a buy, a floor on a sell), with the client id `algo-<id>-<n>`. Nothing rests, so a crash or a cancel-all leaves no order behind, and a limit the market has not reached fills nothing and the amount carries on.

A job checks every 3 seconds and calls Alpaca only while one is working. The state is in `data/algos.json`, so a restart carries on; the deadlines are clock times, so a laptop that slept does not stretch the horizon: when it wakes, the slice for the interval it is in goes out and the rest is spread over the intervals left. After the end time nothing is sent, and the order finishes `done` or `ended` with the quantity left (`6 of 10 not filled`). A refusal from Alpaca ends it as `failed` with the reason, and a busy broker is retried on the next tick. A slice that is still open when its interval is over is canceled once.

A market slice of a coin is cut to what the order book takes within `SLICE_SLIPPAGE_BPS` of the best price, and held back while the book's guard would refuse it (a wide spread); the amount carries to the next interval and the order's note says why. Limit slices and stock slices are not touched. The preview names the cap as `book_cap`.

Checked when it is planned: a stock needs the market open, whole shares (at least one a slice) and an end before the close (`The market closes at 16:00 ET; use at most 369 minutes`); a sell needs the shares in the account (`You hold no F to sell`); slices must be 10 seconds apart or more; a coin slice must cost at least \$10. A buy also passes the cash check for the whole order. `POST /orders/algo/preview` returns the same plan, the slice sizes with their times and the arrival price (the mid of the latest quote), and places nothing.

`tilt` (0 to 0.5, off by default) grows a slice by up to that fraction when the best quote's sizes lean towards the side the order is on, and shrinks it when they lean away; the rest is spread again. It is unproven: Alpaca has no order book for stocks, the sizes are IEX's alone on the free plan, the research on queue imbalance is about the next tick, and a paper fill ignores the quote.

**VWAP.** `algo` `vwap` takes a `duration` of 10 minutes or more and no `slices`. Each five-minute interval is weighted by the average share of a day's volume that traded in that bucket over the last 20 full sessions ([execution-research.md](execution-research.md) measures how well that follows a day), and a part-bucket at either end counts in proportion to its length. The profile is read from five-minute SIP bars, which the free plan allows once they are 15 minutes old; half days, trading outside regular hours and the closing print are left out. It is kept in memory for the day, so only the first VWAP of a symbol waits on Alpaca, from about a second to ten or more. A coin's profile is the 24-hour UTC day. An interval whose share rounds to no shares, or for a coin to less than \$10, sends nothing and its amount carries to the next. A VWAP takes no `tilt`; everything else above applies. `POST /orders/algo/preview` lists only the slices that will go out.

**Implementation shortfall.** `algo` `shortfall` takes `slices` and `risk_aversion` (0 to 100, default 1) and is for stocks only. The intervals are equal and the weights are the steps of the Almgren and Chriss trajectory, x(t) = X sinh(κ(T − t)) / sinh(κT), so a slice is its step's share of what is left: the plan is solved again at each interval from the quantity and time that remain, which gives the same slices while everything fills and adapts when one falls short. κ grows with the stock's volatility and the risk aversion and falls with its market impact. Risk aversion is in units of 10⁻⁶ per dollar of variance, the order of magnitude of the paper's example, and a larger number trades sooner; 0 is an even TWAP. (The list this was built from had the scale the other way round: in the model the risk-averse trader front-loads, and nothing back-loads.) Impact follows the paper's example: ε is half the spread, η the spread over 1% of the daily volume and γ the spread over 10%. At planning the volatility is the standard deviation of a five-minute price change over the last 20 sessions scaled to a trading day, the daily volume is their average over regular hours, and the spread is the median of the latest SIP quotes the free plan allows, because the free IEX quote is IEX's book alone. The preview returns these inputs and `urgency` (κT) as `notes`; the ticket shows how much of the quantity falls in the first half. What the settings do on real symbols is in [execution-research.md](execution-research.md).

An order reports what filled, the average price and the slippage against the arrival price in basis points (positive costs money). Placing and canceling are in the audit log (`algo`, `algo-cancel`); the slices are in `data/algos.json`.

**Long only.** Every stock buy is sent as `buy_to_open` and every stock sell as `sell_to_close`. Alpaca checks that intent: a sell with nothing held is refused (`position intent mismatch`), and so is one above the quantity held. The paper account is a margin account and would otherwise open the short. Bracket and OTO must be buys and OCO must be a sell, so no order here opens a short. Crypto cannot be shorted at Alpaca.

**Cash only.** A buy placed here, as an order, an iceberg or an algorithm order, is refused when its cost is more than the cash left after the open buy orders with a price: `A buy costing \$125.00 is more than the \$100.00 of cash left after open buy orders; this account does not borrow`. The cost is quantity times the limit or stop price, or the last trade on the configured data feed for a market or trailing order (a bracket or OTO on its entry; an iceberg or an algorithm order on its whole size). If no last price can be read the check is skipped and the reason is logged. Sells are not checked, the iceberg's unplaced remainder is not counted against other orders, and the autopilot's orders do not pass through the check, because it sends its sells and buys together. There are no other limits, such as a largest order or a daily loss, because none were given.

**Order book guard.** A market order on a coin is first put to the coin's order book ([book.md](book.md)): it is refused when the spread is several times the coin's usual one, when walking the book would cost more than a limit in basis points over the mid, or when the book holds less than the order. The refusal names the figures and says to use a limit order or a smaller size (`A market buy of 7 BTC/USD would pay about 124.7 bps over the mid; use a limit order or a smaller size`). Limit orders, stocks, icebergs and the parent of an algorithm order are not judged, and a coin whose book is not ready is not either. The three limits are `MAX_SPREAD_MULTIPLE`, `MAX_SLIPPAGE_BPS` and `SLICE_SLIPPAGE_BPS` in the environment; 0 turns one off.

**Audit.** Every manual order, change, cancel, cancel-all, iceberg and algorithm order is written to the audit log, `data/audit.jsonl`, whatever its outcome: `accepted`, `refused` (by Alpaca, by the checks here, or because the request was malformed and never reached the order code) or `failed` (connection lost, Alpaca error). An entry holds the action, the request, the outcome, the reason and, if accepted, the order id and status. A fault in the log never undoes or blocks an order. The slices of an iceberg are in `data/icebergs.json`, not in the audit log. The autopilot's orders are in its run records.

**Ticket.** The ticket asks `GET /orders/rules` for the symbol and quantity and offers only what comes back: crypto gets market, limit and stop-limit; fractional quantities drop the trailing stop and the exits; whole shares get everything. A trail is entered in dollars or percent. "Exits" takes a take-profit and a stop-loss: both or either on a buy (bracket or OTO), both on a sell (OCO). On a sell, "Lots to sell" lists the symbol's open lots with a quantity for each; a plain sell saves that choice against the order for the ledger's specific-lot view, and an exit pair, an iceberg or a buy does not. The confirm dialog lists every price, the time in force, the lots chosen and the estimated total; for a market order on a coin it adds the expected fill from the order book and has no Confirm while the book advises a limit order. In the open-orders tab, Modify opens the selected order's prices, quantity and time in force and sends only what differs, and Cancel all asks before canceling every open order and stopping every iceberg. The open-orders and history tables add the class, limit, stop, trail and time in force, and list iceberg and algorithm orders (working ones under open orders, the rest under history; an algorithm order shows what filled, the average price, the slippage against arrival, the slices sent and when it ends). "Iceberg" in the type list asks for a limit price and "Show at a time". "TWAP" asks for a duration, slices and an optional limit price, with "Follow the quote sizes" under Options; "VWAP" asks for a duration and an optional limit price; "Shortfall" asks for a duration, slices, a risk aversion and an optional limit price. The confirm dialog shows the plan from the preview (for a VWAP, the number of sessions in its profile; for a shortfall, how much trades in the first half), or the reason it cannot run and no Confirm.

## Where the code is

`src/app/features/orders/`

| Module | What it holds |
| --- | --- |
| `rules.py` | the time-in-force table, the checks, the reasons for a refusal |
| `schemas.py` | `OrderRequest`, which runs the checks, `Order`, `Rules`, `IcebergRequest`, `Iceberg`, `AlgoRequest`, `Algo` |
| `service.py` | the Alpaca request for an order, list, cancel |
| `iceberg.py` | `IcebergDesk`: the slices, the job that places the next one, the saved state |
| `algo.py` | `AlgoDesk`: plans an algorithm order, places its slices on schedule, the saved state |
| `schedule.py` | the intervals and the rule for the size of each slice |
| `quotes.py` | the best bid and ask with their sizes |
| `risk.py` | the cash check and the order book check |
| `router.py` | the HTTP routes |
